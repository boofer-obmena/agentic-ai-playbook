**Проблема:** Долговременная память агентной системы (логи, старые версии артефактов, история инцидентов) может многократно превышать доступный объём RAM. Хранить всё в оперативной памяти нецелесообразно экономически и технически. При этом полностью переносить поиск на медленные носители недопустимо из-за деградации времени ответа.

**Решение:** Данные разделяются на два уровня хранения по частоте обращений. Горячий индекс (RAM): данные, к которым обращаются часто — последние N дней, активные задачи, часто запрашиваемые документы. Хранится в памяти, обеспечивает минимальную задержку поиска. Холодный индекс (SSD): исторические данные, архивные версии, редко запрашиваемые документы. Используется алгоритм DiskANN, который строит граф поиска непосредственно на диске, обеспечивая приемлемую задержку поиска без загрузки данных в RAM. Финансовый контролёр управляет балансом между двумя уровнями, автоматически перемещая данные между горячим и холодным индексом по критерию частоты обращений.

**Пример:** Аудитор получает задачу проанализировать инцидент трёхмесячной давности. Данные об этом инциденте находятся в холодном индексе. Поисковый запрос направляется в SSD-индекс. Задержка поиска выше, чем для горячего индекса, но остаётся в пределах допустимого порога. RAM не расходуется на редко запрашиваемые данные.

**Экспериментальная проверка:** Наполнить систему данными, объём которых вдвое превышает доступную RAM. Запустить смешанный поток запросов: 70% к последним данным, 30% к архивным. Проверить: система стабильна, не исчерпывает RAM; время ответа для горячих данных в пределах строгого SLA; время ответа для холодных данных в пределах расширенного SLA.

**История применения:** Не применялся. Раздел заполняется по результатам реального использования паттерна: контекст задачи, что сработало, что потребовало корректировки, итоговые выводы.
