**Проблема:** Обнаружение и маскирование персональных данных (PII) силами самой LLM ненадёжно: модель может пропустить PII или, напротив, ложно идентифицировать нейтральные данные. Кроме того, передача конфиденциальных данных в LLM создаёт риск утечки через обучающие процессы или логи запросов.

**Решение:** До попадания в LLM весь входящий поток данных проходит через быстрый детектор на основе RegEx и малых специализированных ML-моделей. Детектор идентифицирует и маскирует PII (ИНН, названия компаний, персональные данные, номера документов), заменяя их псевдонимами (COMPANY_001, PERSON_002). Таблица соответствий псевдонимов и реальных данных хранится отдельно и недоступна агентам. Дополнительно: «Guard Rails» встраиваются в RAG-пайплайн — документ из базы знаний выдаётся агенту только если агент имеет права доступа к данному документу (проверка по атрибутам документа и роли агента).

**Пример:** Аналитик требований получает запрос с упоминанием конкретной компании: «У клиента ООО Ромашка проблема с...» Препроцессор заменяет название: «У клиента COMPANY_042 проблема с...» LLM работает с псевдонимом. В финальный ответ подставляется реальное название. В логах LLM-запросов фигурирует только COMPANY_042.

**Экспериментальная проверка:** Создать тестовый запрос, содержащий несколько типов PII: ИНН, ФИО, название компании, номер телефона. Пропустить через препроцессор. Проверить: в логах LLM-запросов реальные данные отсутствуют, заменены псевдонимами. Проверить полноту: ни один тип PII не пропущен через детектор.

**История применения:** Не применялся. Раздел заполняется по результатам реального использования паттерна: контекст задачи, что сработало, что потребовало корректировки, итоговые выводы.
