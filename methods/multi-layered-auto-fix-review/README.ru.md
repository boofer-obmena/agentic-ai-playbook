**Проблема:** Агент-Аудитор, обнаружив дефект, способен самостоятельно сгенерировать и применить патч. В большинстве случаев это ускоряет процесс. Однако для критических модулей (ядро финансового учёта, механизмы безопасности, компоненты, затрагивающие производственные данные) автоматическое применение патча без человеческого контроля представляет недопустимый риск.

**Решение:** Для каждого модуля системы определяется уровень критичности (Normal / High / Critical). Процесс применения патча зависит от уровня критичности. Normal: Аудитор генерирует патч → QA верифицирует → автоматическое применение. High: Аудитор генерирует патч → QA верифицирует → создаётся задача ревью для Архитектора → применение после аппрува. Critical: Аудитор генерирует патч → QA верифицирует → обязательное Human-in-the-Loop Gate: задача ревью для Функционального архитектора → применение только после явного аппрува с подписью → уведомление DevOps-агента об изменении критического модуля.

**Пример:** Аудитор обнаруживает баг в модуле расчёта налоговой базы (уровень критичности: Critical). Генерирует патч. QA верифицирует патч на тестовых данных — тесты проходят. Оркестратор создаёт задачу «Ревью автоматического патча» для Функционального архитектора финансовой системы. Патч остаётся в состоянии ожидания. Аппрув архитектора — применение патча с записью в журнал аудита.

**Экспериментальная проверка:** Внести намеренный баг в модуль с уровнем критичности Critical. Запустить Аудитора. Проверить: патч сгенерирован и прошёл верификацию QA, но в релизную ветку не попал — находится в состоянии ожидания Human-in-the-Loop Gate. В системе зафиксировано событие «Merge blocked: Critical module, waiting for Human Approver».

**История применения:** Не применялся. Раздел заполняется по результатам реального использования паттерна: контекст задачи, что сработало, что потребовало корректировки, итоговые выводы.
