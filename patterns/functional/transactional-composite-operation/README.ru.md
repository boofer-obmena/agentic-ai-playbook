# Паттерн 4. «Композитная операция в единой транзакции» (Transactional Composite Operation)

**Проблема:** Многие бизнес-операции требуют нескольких последовательных атомарных шагов. Если один из промежуточных шагов завершится с ошибкой, а предыдущие уже выполнены, система оказывается в несогласованном состоянии: часть данных обновлена, часть — нет.

**Решение:** Сложный сценарий инкапсулируется в единую операцию с полным откатом при любой ошибке на любом из шагов. Либо операция выполняется полностью, либо система возвращается в исходное состояние. В архитектуре явно разграничены два подвида транзакций: Атомарная транзакция (все шаги внутри одной базы данных с ACID-гарантиями) и Компенсационная сага (распределённые вызовы внешних систем — подробнее в Паттерне 13).

**Пример:** QA-агент обнаруживает критический дефект и инициирует операцию «Вернуть на доработку», включающую несколько шагов: создание дочерней задачи, копирование контекста тестирования, обновление статуса, уведомление разработчика. Если на любом шаге произойдёт сбой, Оркестратор отменяет уже выполненные шаги.

**Экспериментальная проверка:** Спроектировать операцию из 4 шагов. Намеренно вызвать сбой на 3-м шаге. Проверить: шаги 1 и 2 отменены корректно, исходная задача не изменила статус, в системе зафиксирован диагностический лог.

**История применения:** Не применялся. Раздел заполняется по результатам реального использования паттерна: контекст задачи, что сработало, что потребовало корректировки, итоговые выводы.
