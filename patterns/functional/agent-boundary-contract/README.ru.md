**Проблема:** Языковые модели могут генерировать выход в произвольном формате: вместо структурированного JSON — эссе, вместо числа — развёрнутое объяснение. Следующий агент в конвейере ожидает определённый формат и при несоответствии завершается с ошибкой или — что хуже — продолжает работу с некорректно разобранными данными.

**Решение:** Каждая граница передачи данных между агентами валидируется Оркестратором через формально описанный Контракт, включающий: JSON-схему с обязательными полями и их типами, бизнес-правила (допустимые значения перечислимых полей), требования к метаданным (в том числе обязательное поле confidence — числовое значение уверенности модели). При нарушении Контракта выход агента отвергается, агент получает точный диагноз несоответствия.

**Пример:** QA-агент генерирует свободный текст вместо структурированного формата. Оркестратор отклоняет пакет: «Нарушен контракт TestResult. Отсутствуют обязательные поля: test_id, verdict.»

**Экспериментальная проверка:** Требуется. Подготовить набор из 10 выходов агента: 7 соответствующих контракту и 3 с разными типами нарушений. Критерий успеха: все 3 нарушения заблокированы с точными диагнозами, все 7 корректных выходов пропущены без ложных срабатываний.

**История применения:** Не применялся. Раздел заполняется по результатам реального использования паттерна: контекст задачи, что сработало, что потребовало корректировки, итоговые выводы.
