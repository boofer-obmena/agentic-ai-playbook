# Generator Executor Pattern

> **Паттерн И10. «Генератор-Исполнитель» (Generator-Executor Pattern)**

**Проблема: Повторяющиеся задачи — ежедневный сбор метрик, парсинг логов определённого формата, регулярные отчёты — каждый раз обрабатываются через LLM. При этом задача идентична: тот же формат входных данных, та же логика обработки, тот же формат вывода. Каждый вызов LLM потребляет бюджет, хотя решение уже было найдено в предыдущий раз.:**



**Решение: Операция разделяется на две явные фазы. Фаза Генерации (Design-time): при первом столкновении с задачей определённого типа LLM не просто решает её, но и генерирует детерминированный исполняемый скрипт (Python, SQL, Shell) для решения аналогичных задач в будущем. Скрипт верифицируется и сохраняется в библиотеке инструментов. Фаза Исполнения (Run-time): при повторном поступлении задачи того же типа маршрутизатор обнаруживает подходящий скрипт в библиотеке и запускает его напрямую, без обращения к LLM. При изменении условий (другой формат входных данных, изменение бизнес-правил) рефлексивный контур (Паттерн 19) перегенерирует скрипт.:**



**Пример: QA-агент впервые получает задачу: проанализировать лог тестирования и выявить все тест-кейсы со статусом FAILED. LLM генерирует Python-скрипт parse_test_log.py, который читает лог определённого формата и выдаёт структурированный JSON с провалившимися тестами. Скрипт сохраняется в библиотеке. На следующий день поступает аналогичная задача. Маршрутизатор запускает parse_test_log.py напрямую. LLM не вызывается. Затраты на обработку задачи: 0 токенов.:**



**Экспериментальная проверка: Выбрать задачу, которая будет повторяться ежедневно (сбор сводки по метрикам, парсинг лога). В первый день зафиксировать число токенов LLM, использованных для решения. Сгенерировать скрипт. Запустить в течение 5 дней подряд. Проверить: начиная со второго дня, LLM не вызывается. Количество токенов = 0. Результаты идентичны.:**
